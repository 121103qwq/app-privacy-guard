# Windows 浏览器 URL 确认故障

## 当前结论

故障尚未修复。不能把浏览器扩展被发现、完整地址栏配置或本地页面已启动，当作工具已经可靠确认当前 URL。

2026 年 10 月 5 日执行了以下诊断，未使用真实 Claude 账号。测试网页只监听 loopback，没有远程资源、认证或公网 IP 基线。

| 检查 | 结果 |
| --- | --- |
| Edge 进程发现 | 通过 |
| 官方 Native Messaging 清单检查 | 通过，名称、路径和允许的官方扩展来源匹配 |
| 扩展资料状态 | 一个资料启用，当前选中的另一个资料禁用 |
| Browser Use 标签页枚举 | 约 21 秒后 `nodeRepl.fetch request failed` |
| 受支持的 Edge 测试标签页创建 | 同样失败 |
| 空白 Edge 本地测试窗口 | 已创建，指定英文界面、完整 URL 显示和辅助功能启动参数；实际显示未通过 UI 读取确认 |
| Window2 目标选择 | 返回同一窗口的重复项，按 app 与窗口 ID 去重后得到唯一目标 |
| 测试窗口状态读取 | 安全检查中止，无法可靠确认 Windows 当前浏览器 URL |

## 已尝试的调整

使用全新测试资料，避免现有账号或已有浏览器状态干扰。为测试资料设置 `omnibox.prevent_url_elisions=true`，使用 `--lang=en-US` 和 `--force-renderer-accessibility`，保留标准浏览器窗口和地址栏。重新从工具返回的窗口对象绑定唯一目标。

这些调整没有消除中止。英文界面和完整 URL 显示只是请求的配置，实际效果尚未确认。扩展启用状态、浏览器连接超时和 Window2 的 URL 确认失败可能相关，但本次证据不足以确认同一个根因。Native Messaging 清单正确也不代表请求通道正常。

## 边界与后续复测条件

安全检查中止后，没有继续 Windows 界面输入，没有伪造 URL、修改检查逻辑或关闭安全检查。未通过重置会话或切换自动化工具继续被拒绝的操作。

下一次允许的诊断应先确认 Browser Use 能实际读取指定测试标签页，再验证 Window2 的标准目标选择、激活和状态读取流程。空白本地页面按钮点击、页面导航和协议弹窗需要分别验证，不能由静态配置或单独 OS 分发结果替代。
